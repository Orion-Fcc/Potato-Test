## 一、跑之前：先把服务起来

1. 双击桌面 `PotatoTest.bat` → 菜单 **1（启动）**。
   - 改过代码/配置必须走这个重启，让新代码生效。
   - 服务后台常驻，关黑窗口不停；再双击一次进 **2（关闭）**。
2. 浏览器开 <http://127.0.0.1:18081/>。
3. 进对应项目（飞行学员管理 / 培训资源管理）。

---

## 二、看失败清单（知道"现在该做什么"）

入口：**项目 → 概览** 页，最上面那张卡片就是**失败清单**。

### 1. 读清单

- 卡片标题行右侧有计数：`未通过 N · 归为 M 类原因 · X 条待人工确认`。
- 每个**分组**是一个"相同原因"的批次，展开（点 `+`）能看：
  - **动作徽章**（该做什么）：
    - 红色 `提缺陷` → 找开发（只有"产品缺陷"走这里）
    - 蓝色 `改用例` / `修数据` → 改用例或补数据
    - 黄色 `查环境` / `人工判断` → 环境或根因冲突
    - 灰色 `重跑` → 直接重跑即可
  - 组内每条用例：`用例号 名称`，失败多次会标 `（失败 N 次）`，下面一行是最近一次的判定理由。
- 看到 **`根因冲突，需人工判断`** 的组：同一组里判定器给出了不同根因，**已按人工确认处理**，别按"多数决定动作"。

### 2. 补全分类（点一下才花额度）

- 右上角 **「补全分类」** 按钮会调 LLM 给历史没分好类的结果补 `root_cause`，**结果落库缓存**，之后不会重复调。
- **默认进页面是不点它的**（首屏快、省额度）。只有看到"待人工确认"偏多、或想让分组更细时再点。
- 点完变 `正在补分类…`，十几秒内回来。某条分类明显不对，清掉该条缓存重新回填即可。

### 3. 清单是自动的，别手工维护

- 清单是**派生视图**：某条用例一旦通过，自动从这里消失。
- 合并靠确定性证据（同因才合），**不做"按标题相似度"的二次合并**——合并错比不合并不糟，人会照着清单查一个不存在的问题。

## 三、让助手按清单改用例（改动留痕）

1. 进 **助手** 页，直接说自然语言，例如：
   > `按失败清单把该改的用例改掉`
2. 助手读清单 → 只对"改用例"类动作动手 → 通过 `x-change-source: assistant` 改用例。
3. 改动**自动写进审计表 `case_change`**，记录：改了哪个字段、改前、改后、谁改的、来自哪条清单。
4. 用例**跑通之后**，对应清单分组自动消失（见第二节第 3 点），不需要你去删。

### 查改动记录（审计）

目前**没有界面入口，走接口**（`case-changes` 只有 API，前端尚未挂面板）：

```
GET http://127.0.0.1:18081/api/projects/{pid}/case-changes?limit=100
```

- `{pid}` 填项目 id；`limit` 默认 100。
- 返回 `case_change` 记录列表，可核对"助手到底改了什么"。

## 五、判定更严了，怎么看"通过/失败"更可信

这轮加了防"假通过 / 假缺陷"的确定性校验，你不需要做任何操作，但要知道**判定口径变了**：

| 现象 | 现在会怎样 |
| - | - |
| agent 结论里写"查询后应有 N 条"，但步骤里从没真读过查询结果 | 判 **failed**，理由写"未测到"，不算缺陷 |
| 最后一步 `action=done` 但同一步还在执行中 | 判 **执行未完成**，不算产品缺陷 |
| 整段都是工具回显、没结论 | 判 **证据不足** |
| agent 一遇障碍就说"无法完成"就停 | 提示词已治住：会换路多试，不再第 1 步就放弃 |

- 想看判定细节：结果里折叠的 **Judge / Final answer**，看"判定理由 + 依据步骤 + 最终回答"。
- 拿那条老被误判的**"使用范围 + 状态同时选 → 点查询"**做试金石：操作对的话，现在不该再被判错。

## 六、出问题的快速定位

| 症状 | 先看这里 |
| - | - |
| 页面打不开 | `logs/potato.log` 最后几行；端口是否 18081 |
| 跑用例报"找不到浏览器" | 系统 Edge 没被探测到；`跑批前体检.bat` 过一遍 |
| 整批用例全 error、无结论 | 历史回归是 `await` 同步 sleep，现已修；若复现看日志有无 `TypeError: ... await` |
| 429 / 网关报错 | LLM 额度耗尽，代码层不解决，跑大批量前留意额度 |
| 清单"几乎没合并" | 点一次「补全分类」补根因，再刷 |

## 七、给 WorkBuddy agent 用的 MCP 接口（24 工具）

想让 agent（WorkBuddy 里的助手）直接操作 Potato，不用人点界面，走这套 stdio MCP。
它**不侵入 FastAPI 本体**，独立进程 `potato_mcp_server.py` 用 httpx 调本机 REST（默认 `127.0.0.1:18081`）。

### 1. 怎么接

- WorkBuddy 连接器用 stdio 拉起：`.venv/Scripts/python.exe potato_mcp_server.py`（项目 venv 里）。
- 本机 `AUTH_ENABLED=false` 免 token；开了登录就设 `POTATO_COOKIE` 传 `tp_session`，`POTATO_BASE_URL` 可换地址。
- 读工具零副作用；写工具（跑运行 / 改用例 / 改判 / 删 / 导入）在工具描述里标清，agent 看得到。

### 2. 五组、24 个工具

| 组 | 工具 | 说明 |
| - | - | - |
| 1 只读查询（10） | `list_projects` / `list_testcases` / `get_testcases_by_status` / `get_failure_digest` / `get_case_changes` / `list_runs` / `get_run` / `get_run_results` / `get_case_results` / `get_project_stats` | 全是 `GET`，零副作用 |
| 2 运行控制（3） | `start_run` / `rerun_run` / `cancel_run` | 会真的起浏览器跑，耗时数分钟起；本机并发硬限 1 |
| 3 用例编辑（3） | `create_case` / `update_case` / `delete_case` | 写改动自动带审计头进 `case_change`；删走双闸门（见 3） |
| 4 人工改判（2） | `override_result` / `revert_result_override` | 覆盖 AI 结论并留 `original_status` 可撤销 |
| 5 账号/配置/导入（6） | `list_credentials` / `create_credential` / `delete_credential` / `recheck_credential` / `set_project_roles` / `import_cases_from_xlsx` | 2026-10-08 补齐，见下 |

### 3. 第 5 组要点（本轮新增）

- **密码只进不回显**：`create_credential` 的 `password` 只在本次请求里传，服务端加密存储，`list_credentials` 回的是脱敏结构（含 `healthy`/`last_error`，**不含明文**）。传 `credential_id` + 新密码 = 密码轮换，不丢 role / 会话缓存。
- **删账号有双闸门**（和 `delete_case` 同款）：
  - `dry_run=True` 只看预览（该账号是谁、影响哪些角色），不动任何东西；
  - 真删必须原样传 `confirm_delete="确认删除"`，缺了就被拒绝、退回预览。
- **批量导入走 `import_cases_from_xlsx`**：Potato 唯一批量导入通道（模板 18 列，可从 `GET /api/projects/{pid}/testcases/template` 下载）。默认 `overwrite=False` 只追加；`overwrite=True` 会**先删与文件 case_key 冲突的既有用例**再导入，同样双闸门——真覆盖必须传 `confirm_overwrite="确认覆盖"`，缺了拒绝。
- **`set_project_roles` 是整体替换**：用例 Role 列取值必须落在项目 roles 列表内，改完先 `list_credentials` 确认每个角色都有账号，否则执行报「角色没有可用账号」。

> 危险操作（删用例 / 删账号 / 覆盖导入）都要先预览、再带确认词真删——比「直接调」保守，agent 不会顺手把数据删了。
