# Potato Test 使用说明

> 用**自然语言**写测试用例，让浏览器 Agent 真的去点，再由 LLM 裁判判定「通过 / 失败」并写出理由。
> 用例是提示词，不是脚本 —— 页面改版、元素挪位置，用例不用改。
>
> 本文是**操作手册**：怎么启动、怎么配、怎么写用例、怎么看结果、出问题怎么查。
> 想知道"它是怎么实现的"看 [README.md](../README.md)；想改配置项看 [configuration.md](configuration.md)。

最后更新：2026-10-05

---

## 1. 启动与关闭

### 日常使用：桌面版（安装后双击图标）

装好 `PotatoTest-Setup-1.0.0.exe` 之后，开始菜单里有「Potato Test」，
**双击就打开一个独立窗口**（不是浏览器标签页）。桌面快捷方式看安装时有没有勾（默认不勾）。

它会自己处理这些事，不需要你管：

- **关窗口 = 服务停止**，不会留后台进程，也不会留下孤儿浏览器
- 数据库、上传的原件、浏览器 profile 都落在**程序目录旁边**
  （默认 `%LOCALAPPDATA%\Programs\PotatoTest`）—— 所以别装到 `Program Files`，那边不可写
- 日志写进程序目录下的 `logs\desktop.log`
- 端口默认 **18081**；被占用时**自动换一个空闲端口**，不用管

> 从源码跑也行：`python desktop.py`。装了 `pywebview` 就是原生窗口（Edge WebView2），
> 没装会自动退化成 Edge 的应用窗口 —— 都不用浏览器地址栏。

**更新**：设置页最下面有「版本 → 检查更新」。查到新版本后点「下载并安装」——
应用会自动退出并静默覆盖安装，**数据（项目 / 用例 / 原件）不动**（它们跟程序文件是分开的）。

> 网页版只能看到"有新版本"，装不了：它跑在服务器上，改不了你本机的程序。
> 更新包只从本项目的 GitHub Release 下载（地址白名单写死在 `app/updater.py`，
> 不是任意链接都能装 —— 这个接口会执行下载下来的 exe，不能放开）。

### 手动启动（部署到服务器 / 想在前台看日志时）

```bat
cd /d D:\<项目目录>
.venv\Scripts\python run_server.py 18081
```

前台方式的日志直接打在窗口里，**关掉窗口服务就停**。

停止后台服务：

```bat
taskkill /F /FI "IMAGENAME eq pythonw.exe"
```

### 打开界面

- **桌面版**：窗口里就是界面，不用管地址。
- **手动起的服务**：浏览器访问 <http://127.0.0.1:18081/>。

> 网页版和桌面版是**同一套服务**：同一台机器上用浏览器打开，功能和桌面版完全一样，
> 不需要另外部署服务器。只有"给别人用"才需要把服务部署到一台机器上（见 `docs/deployment.md`）。

## 2. 第一次使用要配什么

按顺序做这四步，**第 2 步别跳过**。

1. 打开 <http://127.0.0.1:18081/>（端口固定 18081）
2. 进 **管理员 → 系统设置**，找到 LLM 模型那一块，填 Base URL / API Key / 模型名，
   点**测试连通性**，确认能通
   - 这一步跳过的话，后面每次运行都会失败，而且报错看起来像用例写错了，很难查
   - 当前本机用的是 `example-model`，网关 `https://api.example.com/v1`
3. **新建项目**，填被测系统的地址（本机是内网培训管理平台）
4. 进 **项目 → 设置**，配**环境**和**登录账号**（见下一节）

> 界面里的 LLM 配置**优先于** `.env`，改完立即生效，不用重启服务。

### 配环境与账号

- **环境**：一个项目可以有多个环境（测试/预发…），base_url 挂在环境上。
  不建环境也能跑，但用了环境绑定账号时就匹配不上了。
- **账号**：在 **项目 → 设置** 里添加。两种类型：
  - `password` —— 存用户名密码，服务端会自己登录一次并把会话捕获下来复用，
    所以用例不需要每次重新登录
  - `storage_state` —— 直接粘贴/上传别人导出的登录态
- **角色（role）**：账号可以打角色标签。一条用例声明"以审核员身份执行"时，
  系统就按这个标签去挑账号。同一个角色可以配多个账号。

## 3. 界面导航

点进一个项目后，左侧菜单是这样组织的：

| 分组 | 菜单 | 干什么 |
| --- | --- | --- |
| 顶层 | **项目** | 项目列表，从这里进具体项目 |
| — | **概览** | 通过率、失败数、最近运行等 KPI |
| — | **助手** | 内置对话助手，可以查用例/跑测试/看报告/起草用例 |
| 测试资产 | **测试用例** | 用例的增删改查、Excel 导入导出、发起运行 |
| 测试资产 | **套件** | 把一批用例存成一个可复用的集合，可定时提醒 |
| 结果 | **运行** | 每次运行的进度与结果，支持"只重跑失败的" |
| 结果 | **对比** | 挑几次运行摊成矩阵（用例 × 运行），看哪些从通过变失败 |
| 结果 | **问题** | 缺陷看板，失败的用例可以直接转成缺陷单 |
| 项目 | **成员** | 仅开启登录后有意义 |
| 项目 | **设置** | 环境、账号、项目级参数 |
| 管理员 | **用户 / 系统设置** | 仅 `AUTH_ENABLED=true` 时出现 |

> 本机是 `AUTH_ENABLED=false` 单人本地模式，**管理员**分组不显示，"成员"也没有实际作用。

## 4. 写用例

### 4.1 一条用例包含什么

| 字段 | 说明 | 必需 |
| --- | --- | --- |
| 用例名称 | 给人看的标题 | 是 |
| Agent 任务 | **用大白话写的操作要求**，这是真正被执行的提示词 | 是 |
| 预期结果 | 判断依据，裁判按它下结论 | 是（否则无法判定） |
| 前置条件 | 执行前需要具备的数据/状态，见 4.2 | 否 |
| 测试数据 | 要用到的具体数据 | 否 |
| 起始地址 | 从哪一页开始，留空用环境的 base_url | 否 |
| 角色 | 以哪个身份执行，见 4.3 | 否（留空用项目默认账号） |
| 模块 / 标签 / 优先级 / 类型 / 负责人 | 分类与筛选用 | 否 |

**Agent 任务**写成"要做什么"，不要写成"点哪个按钮"：

- 好：`以审核员身份登录，打开待审批列表，通过第一条，确认状态变为已通过。`
- 差：`点击左上角第三个菜单，再点第二行的"通过"按钮`

前者页面改版了也不用改；后者元素一挪就失效 —— 那还不如写脚本。

### 4.2 前置条件怎么写

系统对前置条件的处理分三种情况，**都不需要你写脚本**：

1. **条件已满足** —— 直接开始执行。
2. **条件不满足，但系统自己能造** —— Agent 会**自己按真人操作把数据造出来**再继续。
   比如前置写"已存在一条待审核的申请单"，列表却是空的，它会自己去新建一条。
   三条限制：只造该造的、造完必须**回页面确认真的存在**、造不出来会如实报"被阻塞"，
   不会假装已满足然后照常判通过。
3. **前置条件里引用了其他用例** —— 直接写用例编号，例如：

   ```
   已存在由 TC-008 创建的申请单
   ```

   系统会把 `TC-008` **自动提到前面先跑**，跑完再跑本条。
   支持链式依赖（A 依赖 B、B 依赖 C），也能处理互相引用不会死循环。

   > 注意：编号**只在同一个项目内解析**。不同项目的用例编号可能重名，
   > 跨项目引用会让项目耦合在一起，所以系统不认。

### 4.3 多角色用例

一条用例如果要在流程中间**换成另一个身份**（典型场景：申请人提交 → 审批人审批），
就把角色填成**有序列表**，例如"申请人 → 审批人"。

Agent 会在流程中自己切换账号。只需要一个身份的用例，按单角色写就行 ——
**单角色用例的执行方式完全不变**。

### 4.4 Excel 批量导入导出

在 **测试用例** 页可以导出全部用例为 Excel，改完再导入。

列的顺序：

```
Case Key | Module | Name | Priority | Type | Status | Owner | Tags | References |
Preconditions | Agent Task (prompt) | Steps | Test Data | Expected | Start URL |
Enabled | Role
```

几点提醒：

- **整份导出 → 改 → 再导入** 是安全往返，包括角色列
- `Case Key` 留空会**自动分配**编号（`TC-001` 这种），不用手填
- `Enabled` 接受 `1/true/yes/是/启用` 这些写法
- 编号**只在项目内唯一**。两个项目都从 `TC-001` 开始是**正常设计**，不是重复

### 4.6 从需规文档生成用例（2026-10-09）

用户的原话是："我发需规或者相关的系统文件项目文件给他，然后他能帮我生成测试用例，
然后并进行测试。" 这条路现在有**两个入口**，都通向同一套逻辑（`app/specgen.py`）：

* **网页**：测试用例页 → 从需规生成
* **助手**：直接把文件发给内置助手，或说"用 XX 文档生成用例"

流程是四步，**刻意不做成"一键全生成"**：

1. **上传文档**：面板里点「上传需规文档」，或在设置 → 需规 / 资料上传。
   支持 **md / txt / json / csv / docx / pdf / xlsx / html / rtf**（见 `app/docparse.py`）。
   默认是**追加**（一个项目的需规常常是好几份文件）；要整份替换得显式说明。
   - 上传接口会**顺带规划**并返回模块清单，所以"发文件 → 能生成"是一步，不是三步。
   - 解析警告会显示出来（空文档、图片型 PDF、没有标题）。**别忽略它**：
     一份扫描件"上传成功"但提取不到文字，看起来和成功一模一样。
2. **分批规划**：模型把文档标题归并成若干**测试模块**，并标出哪些模块在浏览器里
   根本测不了（性能指标、数据库约束、部署运维）。
   - 一份 46 万字的合并需规实测有 **586 个章节标题**，所以规划是**按文档顺序分块**做的
     （每批 60 个）。界面会显示"已规划 60 / 586"，可以逐批继续 ——
     不这么做的话，前 60 个之外的标题会被静默丢掉，用户还以为文档就这么大。
   - 规划失败（网关不可用等）会**退化成"一个小节一个模块"**并标 `degraded`，
     而不是回一个空列表 —— 文档已经入库了，此刻用户要的是"能生成"。
3. **逐节生成草稿**：选一个模块 → 模型只根据**那一节的正文**起草用例。
   生成结果**不落库**，先在右侧给你看、可编辑、可逐条丢弃。
   被解析层拒掉的用例会连**原因**一起列出来（"预期不可判定"这类），不静默丢。
4. **审阅后入库**：两个按钮 —— "存为草稿"（默认）和"存并启用"。

**草稿不会进回归集。** `run-all` 的取数口径是 `enabled=true` **且** `status=active`，
所以生成出来的东西在没人过一眼之前不会被跑到。
（2026-10-09 修：这个口径原来只看 `enabled`，而生成的草稿是
`status="draft", enabled=True` —— 于是"草稿不会被跑到"在 run-all 上是**假的**。
现在有 `tests/test_case_status_human.py` 用 run-all 的**实际结果**守着它。）

几个刻意的质量约束（都在 `app/specgen.py`）：

- **只有文档里写明的需求才会变成断言**。"建议 / 可选 / 待确认"的内容不生成用例 ——
  那会造出永远失败且无法反驳的用例。
- **预期为空或同义反复（"符合预期"）的草稿会被丢弃**。这类 expected 在界面上看起来
  像填了，是审阅最容易放过的一类，但它在语义上等于没有预期。
- **一条用例一个断言**。多个断言会让失败原因无法定位。
- **模型不许发明标题**。规划阶段只能用清单里真实存在的标题（按编号引用），
  否则那些标题下面没有原文，生成出来的就是纯编造。
- **标题与正文严格对应**。文档里小节的标题是从 chunk 正文重新扫出来的，
  不是读 `KnowledgeChunk.heading` —— 后者在"小段落被合并成一个 chunk"时会漏掉标题，
  并把下一节的正文算到上一节头上（真库 project 2 实测：175 → 43 个真实小节）。

### 4.7 后端接口探索（2026-10-09）

用户的原话："我希望这个系统也具有探索后端的能力……他需要有探索后端的能力去拿到
这个菜单或者相关的数据。"

菜单、列表这类内容往往是**后端返回的**（前端拿 `/api/menu` 渲染侧边栏），
所以只知道点界面的测试，没法写出"页面显示的菜单和接口返回的一致"这种断言。
项目概览页现在有一块 **从页面流量里学到的后端接口**。

**怎么学到的：观察，不是扫描。** 页面为了渲染必然要调后端，那些请求就是权威答案 ——
不用猜路径、不用撞目录，也不会朝服务器发它没被设计来处理的请求。
实现挂在已有的 CDP 请求拦截上（`app/browser_hygiene.py` 本来就在为拦第三方 beacon
而拦截全部请求），所以开着它**零额外开销**。

几个要点：

- **没跑过用例就是空的**，这是"观察式发现"的固有代价，界面上会直接告诉你先去跑一轮。
- **路径会归一化**：`/api/user/1024/detail` 和 `/api/user/2048/detail` 是同一条
  `/api/user/{id}/detail`。不归一的话，翻两页、点开三条详情就能造出十几条"不同"接口。
- **只存参数形状，不存值**：`?token=eyJ...` 只记成 `token: opaque`。请求头一律丢弃，
  请求体只取顶层字段名。所以这张表即使被导出来也不含凭据或业务数据。
- **写接口只登记、不调用**：POST/PUT/DELETE 会被列出来（你需要知道系统有哪些写接口），
  但界面上标"只能看"、点不了，后端也会拒。探索阶段的写请求一旦发出去，
  就可能在你测试环境里建/删真数据 —— 那代价不是"少拿到一点信息"能比的。
- **读接口可以点"读数据"**：会用项目已保存的登录态发一个只读请求，把返回的
  JSON 显示出来，用来核对"菜单项是不是真的来自这个接口"。
  只允许调用**已经观察到**的接口 —— 这一条把"探索"和"扫接口"彻底分开。

生成的用例会自动带上接口清单（见 `app/api.py::_api_context_note`），
所以模型写断言时可以核对接口返回的数据，而不是只断言"页面上有某个元素"。

### 4.8 助手会做前置准备，也会反过来问你（2026-10-09）

用户的要求是："可以允许 agent 做一些前置准备包括但不限于探索后端，搜索相关网页，
询问我需要一些信息"。助手现在多了这几个工具：

| 工具 | 什么时候用 |
|---|---|
| `spec_modules` | 生成用例的第一步：看文档能分成哪些可测模块（支持分批） |
| `spec_draft_cases` | 针对一个模块起草用例（**不落库**，先给你看） |
| `spec_save_cases` | 你确认后落库（默认仍存草稿） |
| `observed_endpoints` | 看从页面流量里学到的后端接口 |
| `web_search` | 核实**通用标准**（行业口径、第三方组件默认行为、兼容性要求） |
| `ask_user` | 需规没写清、信息不足以写出可判定断言时，**问你** |

**`ask_user` 会真的把这一轮停下来。** 如果问完继续往下跑，模型几乎必然用自己猜的
答案把剩下的做完 —— 那就等于没问。界面会显示问题（可能带候选答案），你回答后它继续。

`web_search` 有个**刻意的边界**：它只能用来核实通用标准，**不能**用来查被测系统自己的
业务规则。联网搜到的"类似系统怎么做的"不是需求，据此写断言等于编造 ——
业务规则必须来自需规（`search_knowledge`）或你本人。

### 4.9 人来变更用例状态：草稿 / 生效 / 废弃 / 受阻（2026-10-09）

用户的原话："用例也加上人可以变更状态的功能，因为有些用例 agent 可能执行不了"。

四个状态的语义**刻意分开**：

| 状态 | 含义 | 后续动作 | 进回归集？ |
|---|---|---|---|
| `draft` 草稿 | 生成了，还没人审 | 审阅 → 启用 | 否 |
| `active` 生效 | 审过了，可以跑 | 跑 | 是 |
| `blocked` 受阻 | **有效**，但当前跑不了 | 想办法解决原因 | 否（自动移出） |
| `deprecated` 废弃 | 这条不要了 | 删 | 否 |

`blocked` 和 `deprecated` 分开是有原因的：混在一起的话，看清单的人分不清
"该删的"和"该想办法的"，而这两者的后续动作完全相反。

用法：测试用例页勾选用例 → 顶部「标为受阻」/「启用」（可批量）。
**标为受阻必须写原因** —— 只标一个红点的话，下一个人只能把这条用例重新跑一遍
才知道它为什么被挡住，而"重跑一遍"往往要花几分钟，正是这个状态本该省掉的事。
原因会直接显示在列表里，不用点进去。

### 4.10 上传需规 / 资料（2026-10-17）

「项目文档」页左侧的**上传需规 / 资料**。支持 md / txt / json / csv / docx / pdf / xlsx / html / rtf，
以及图片（png / jpg —— 走 OCR）。

一次上传会同时产生两样东西，别搞混：

| 产物 | 进哪里 | 给谁用 |
| --- | --- | --- |
| 解析出的文本 | 知识库（分块） | AI 检索，回答"这个模块有什么规则" |
| 一份项目文档 | 左侧文档列表（标题 = 文件名） | 人看、人改 |

**原件会留下来**（存在 `artifacts/` 下）。文档页上的**「原件」**能直接打开当初上传的那份文件 ——
PDF 的版面、docx 的标题层级、表格的形状，只有原件里才是准的；解析出的正文是有损的。

**正文可以像 Word 一样手工改**，改完点右上角「保存」。两件事必须知道：

- **重传同一个文件不会覆盖你改过的正文**。系统用"解析产物指纹"判断这份正文是否被人动过：
  动过就保留你的版本、只更新原件，并明确提示"没覆盖"；没动过才用新解析结果替换。
  想按新解析重来，把正文清空再传一次。
- 助手也能读原件（`read_doc_source`），但它读 PDF 时仍然只有**文字层** ——
  要精确版面请自己点「原件」看。

### 各格式 AI 到底能读到什么（2026-10-17）

| 格式 | AI 读到的 | 会丢的 |
| --- | --- | --- |
| md / txt / json / csv | 全文 | — |
| html | 全文（转成 markdown） | 样式、脚本 |
| rtf | 全文 | 格式 |
| docx | 全文，**含表格**（段落与表格按原文顺序） | 页眉页脚、文本框、图片里的字 |
| xlsx | 全部工作表的单元格 | 公式（读的是算出来的值）、图表 |
| pdf | 文字层；**没有文字层的页自动 OCR** | 版面、表格形状 |
| png / jpg 等图片 | **OCR 识别**（中英文） | 照片糊/倾斜时会有错字 |

> **OCR 是兜底，不是万能**：它只在"没有文字层"的页上跑（有文字的 PDF 不会变慢），
> 识别结果会在正文里标成「（OCR 识别）」，并且会提示"可能有错字，关键处请看原件"。
> 扫描件质量差时该转 md 还是要转。

**读不全时一定会明说**：上传后如果弹出提示（"有 N 页没有文字层"、"整份文件 3 MB
却只读到 120 个字"），意思就是 AI 看不到那部分。这时两条路 ——
**把内容另存成 .md 再传**（最可靠），或者自己点「原件」核对。

> 为什么要专门做这道提示：最危险的不是报错，而是"读得很少却一声不响" ——
> 界面上显示上传成功，AI 其实几乎没看到东西，后面生成用例就会凭空发挥。

> **大系统共享需规**：在「项目」页某个大系统上点「共享需规」，除了粘贴文本，也能**上传文件**。
> 上传是**追加**（不冲掉已有内容），传过的原件会在弹窗里列出来，随时打开核对。

## 5. 运行用例

在 **测试用例** 页勾选用例 → 点运行。

### 5.1 并发固定为 1（这是内网限制，不是性能没调好）

本机内网只有**一条通道**，所以最大并发锁死在 **1**。

开多个并发不会更快，只会让几个用例互相抢带宽、**一起变超时** ——
那是把"一个用例的等待"变成"多个用例的失败"。所以即使某个项目设置里填了更大的数字，
上层也会兜回去。

### 5.2 步数和超时是"兵底"，不是预算

| 参数 | 当前值 | 性质 |
| --- | --- | --- |
| 单用例步数上限 | 80 | **兵底**，只拦真正卡死的用例 |
| 单用例超时 | 600 秒 | **兵底**，只拦真正卡死的用例 |

**这点很重要**：它们不是"给用例的预算"，而是"防止一个卡死的用例占掉一整夜"。

速度是另外驱动的 —— 系统直接要求 Agent **用最少步数、最快时间完成**，
同时明确禁止为了快而降低验证标准（不许跳过该验证的步骤、不许报告没看到的结果）。

所以如果你看到"步数用尽"，那说明这条用例**真的卡住了**，需要去看它卡在哪一步，
而不是简单地把数字调大。

### 5.3 只重跑失败的

在 **结果 → 运行** 里，对某次运行可以"只重跑失败的"。它按判定结果筛：

- **失败** —— 没通过的
- **错误** —— 压根没跑出结论的（基础设施问题，最值得重试）

### 5.4 套件

如果一批用例要反复跑，在 **套件** 里把它们存成一个集合，之后一键跑整组。

## 6. 看结果

点开一条失败的用例，会看到：

### 6.1 三段式失败描述（直接可以贴进缺陷单）

```
【操作步骤】登录admin->进入培训资源管理->进入资源审批配置->点击批量停用
【实际结果】这两个按钮直接处于禁用状态
【预期结果】未勾选数据时应提示用户先勾选，而不是把按钮直接禁用
```

这三段是 AI 写的，**故意写得很短**，因为要直接粘进缺陷单。
它只写日志里**真实发生过**的动作 —— 不会根据用例标题去补想步骤。

### 6.2 失败根因分类

每条失败都带一个分类标签，**红色 = 要找开发，琥珀色 = 执行侧问题**：

| 分类 | 含义 | 该找谁 |
| --- | --- | --- |
| **产品缺陷** | Agent 确实操作到位了，系统行为与预期不符 | **开发**（唯一算真缺陷的一类） |
| 执行未完成 | Agent 自己没做完，中途停了 | 重试 |
| 证据不足 | 记录里没有能判断的东西（页面没渲染等） | 重试 |
| 前置数据缺失 | 前置条件没有、也造不出来 | 补数据 |
| 账号/权限 | 登录失败、账号被占、没有权限 | 查账号 |
| 环境/网络 | 页面打不开、超时、代理/证书问题 | 查环境 |
| 测试数据问题 | 用例给的数据界面不接受 | 改用例 |
| 用例本身问题 | 预期写得无法判定、依赖已不存在的界面 | 改用例 |
| 无法判定 | 判断不出属于哪类 | 人工看 |

**这是设计上的重点**：只有"产品缺陷"会被算作真缺陷。
"账号在忙""前置数据没造出来"这类**假失败**被单独归到执行侧，
不会污染缺陷率的统计口径。

### 6.3 判定依据

在折叠的"Judge / Final answer"里可以看到：

- **判定理由** —— 为什么判成这样
- **依据步骤** —— 判定器引用了第几步。如果它没说明依据，理由的可信度要打折
- **最终回答** —— Agent 自己怎么说

判定的原则是**证据不足时默认判失败**，不会出现那种"假绿"。

## 7. 经验记忆（自动积累，不用管）

系统会为每条用例自动积累"操作经验"（从哪进、页面加载要多久、哪个按钮挨得近容易点错），
下次跑同一条用例时注入提示词，减少重复摸索。

你需要知道三件事：

1. **它只记过程和界面知识，绝不记判定结果** ——
   不会出现"上次这条通过了，所以这次也通过"这种背答案。这是硬红线。
2. **用例一改，记忆立即作废**（靠内容指纹判断），不会拿旧经验误导新用例。
3. **首跑的用例也能借到经验** —— 系统会从**同项目其他用例**的记忆里，
   按相关度挑出可迁移的界面知识（页面特性、元素注意事项）一起注入。
   但**不会共享导航路径**，因为那是每条用例专属的，借错了反而把人带偏。

## 8. 项目隔离（重要，改数据前必读）

**默认隔离，关联由你显式建立。**

| 资源 | 隔离方式 |
| --- | --- |
| 用例、运行、结果、缺陷、套件 | 按项目分开 |
| 账号、环境 | 按项目分开，**绝不跨项目取用** |
| **浏览器缓存 / cookies / 登录态** | 按项目分目录持久化，项目之间**不共用** |
| 用例编号 | **只在项目内唯一**，跨项目可以重名 |
| 用例经验记忆 | 只共享同项目 |
| 登录用户 / 知识库 / LLM 配置 | **全局共享**（这两项是有意共享的） |

为什么强调这个：不同项目之间**可能有业务关联，但具体关系只有你知道**。
系统不会替你"顺手打通"（比如自动复用另一个项目的账号、
按编号跨项目引用用例），因为一旦打通，你会在不知情的情况下拿到一份混合了
两个项目数据的报告。

**想要跨项目能力，先想清楚关系，再改代码。**

完整说明见 [PROJECT_ISOLATION.md](PROJECT_ISOLATION.md)。

## 9. 飞书机器人（本机已开启）

可以在飞书群里远程触发查询，**不用开电脑**。

先在群里发：

```
@机器人 绑定 <项目名>
```

绑定后可以用自然语言问它，例如：

- 最近一次运行怎么样？通过率多少？
- 现在有多少启用的用例？
- 有没有失败的？
- 帮我新建一条用例草稿

能做的事：查运行状态/通过率/完成时间、查用例数量（启用/总数）、
查缺陷列表、**新建用例草稿**（草稿状态，需要人工确认后才启用）。

也可以直接下指令（与群里的「帮助」卡片一致）：

| 指令 | 作用 |
| --- | --- |
| `@机器人 状态` | 立刻回一张进度卡（在跑的显示进度，没在跑的显示最近一次结果） |
| `@机器人 跑 [项目名]` | 先弹**确认卡片**，你回一句 `确认` 才真的跑；回 `取消` 就不跑 |
| `@机器人 重跑` | 重跑最近一次 |
| `@机器人 重跑失败` | 只重跑最近一次里**未通过**的那些（与界面「只重跑失败的」同一套筛选） |
| `@机器人 改判 <结果号> 通过\|失败 [理由]` | 人工改判一条结论，与界面上的改判写同一批字段 |
| `@机器人 绑定 <项目名>` | 把本群和项目绑起来 |
| `@机器人 帮助` | 列出以上说明 |

两点值得知道：

- **确认卡片不能点按钮。** 服务通过轮询读群消息，收不到卡片按钮的点击事件，
  所以卡片是给你看的提示，真正开跑靠你在群里回一句 `确认`（10 分钟内有效，
  过期要重新发起）。回 `取消` 则作废。
- **`重跑失败` 走的是与界面完全相同的筛选口径**：`passed` 之外全算
  （`failed` 和 `error` 都重跑，没有结果记录的也算）。卡片上会写明"只重跑未通过的 N 个"，
  避免把部分通过率误读成全量通过率。

它只查真实数据，不会编。未绑定项目时会提示你先绑定。

> 想关掉：在 `.env` 里设 `ENABLE_FEISHU=false` 后重启服务。

## 10. 排障

**启动后浏览器打不开 / 连不上**
看启动脚本的提示（端口固定 18081）。也可以直接看 `logs/potato.log` 的最后几行。

**点"运行"报 `No module named 'browser_use'`**
依赖没装全：

```bat
.venv\Scripts\python -m pip install -e .
```

这类依赖是懒加载的，缺了不影响服务启动，只在真正跑用例时才暴露。

**报"找不到浏览器"**
Chromium 没下载：

```bat
.venv\Scripts\python -m playwright install chromium
```

**用例老是失败，报错看起来都差不多**
先看**失败根因分类**（第 6.2 节）。如果一大片都是"环境/网络"或"账号/权限"，
那是一个环境问题，不是一堆用例坏了 —— 别去改用例。

**报"步数用尽"**
这条用例真的卡住了。去看它卡在哪一步，而不是把步数调大。
报错里会区分"步数用尽"和"卡在某一步"，两种情况处理方式完全不同。

**为什么界面里没有"管理员"分组 / "用户管理"？**
因为是单人本地模式（`AUTH_ENABLED=false`）—— 没有登录就没有"用户"这个概念。

**改了 `.env` 没生效**
`.env` 里的值**优先于** `app/config.py` 里的默认值，改代码前先确认 `.env` 有没有同名键。
另外注意 **`.env` 里同一个键不要写两遍**，dotenv 取**最后一次**出现的值 ——
只改一处会看起来"改了没生效"。

**写 `.env` 时注释要单独占一行**
写成 `KEY=   # 说明` 的话，dotenv 会把 `# 说明` 当成值。
